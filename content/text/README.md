# content/text: every word an id

Every line of original English a player can see lives here, by id, and nowhere else (decision 21; GAME_DESIGN 18, BUILD_PLAN 10). Code and pages carry ids; the build fills in the words for each channel. This README is docs, not game text.

What each channel ships is set in `content/scope/m1a.json`.

## One line

```json
{
 "app.offline": {
  "text": "Works offline",
  "ctx": "A small stamp, once the game is saved on the phone",
  "screen": "app",
  "max": 24
 }
}
```

- **id:** `<area>.<thing>[.<detail>]`, lowercase letters, digits and underscores, joined by dots. The area is the file: `app.*` lives only in `en/app.json`.
- **`text`:** the working words. `{var}` for a variable, `{UPPER}` for a placeholder (T13), `*emphasis*` as the one markup, `\n` for a line break, never HTML. A plural is `{"one": "...", "other": "..."}`, picked by the `n` variable.
- **`ctx`:** the note a batch shows: where, when, what it has to do.
- **`screen`:** the screen it shows on (`app`, `title`, `credits`, `debug`, `guestbook`, `trail`, `lockbox` so far; a line whose screen isn't built yet waits for it).
- **`max`:** the character limit, required for class `ours`: lint T15 holds every form to it (below). A dev line may have one, and is held to it if it does.
- **`class`:** `ours` (the default: the creator approves every line) or `dev` (the debug menu and the bug report: exempt, decision 64). Later: `yours`, `quote`. Real place names and terms aren't lines at all: they live in `names/` (below).

There is no status field.

## The four states

Status is worked out by comparing the working words with the ledger, never typed (18.4). The hash is SHA-256 of the words after Unicode NFC (a plural: canonical JSON with sorted keys).

| State | Means | Main ships |
|---|---|---|
| draft | No approval on record | Nothing: the main build stops |
| approved | The ledger's hash matches the working words | The words |
| changed | Approved once, edited since | The ledger's frozen words, until the new ones are approved |
| cut | These exact words were vetoed | Nothing, anywhere (preview shows them empty) |

Two more fall outside approval: a `dev` line, and a line with no letters once its `{vars}` are gone (`app.build`, the bare build code), which has no words to approve.

## Adding a line (any session)

1. Write it in its area's file as a draft: `text`, `ctx`, `screen` and `max`.
2. Use it: `data-t="id"` (or `data-t-attr`, `data-t-img`) in a page, `t('id')` or `tx(el, 'id')` in code.
3. If it lands on a screen main carries, add it to `main.off` in `content/scope/m1a.json` with a reason, until it is approved. Otherwise the main build fails (T14).
4. List it for the session's batch. Keep new lines to the minimum.

Approved lines are left alone: a change goes in the next batch, and main keeps the approved words meanwhile.

## Lines the content names

Content files name lines too, never words: a field such as a stop's `box` or a choice's `label` holds `"@trail.sol_duc_trailhead.lot"`, an `@` and the id (its schema marks it `"x-text": true`). The build sends the ids to `data/voice.json`, the engine hands them to the page as refs (`{id, vars}`), and `tx()` turns them into words. Code that shows such a line has no literal id to give, so its call ends `// t-ids: @content`:

```js
tx(p, ref.id, ref.vars); // t-ids: @content
```

The lints follow the content: every `"@id"` in `content/**/*.json` (outside `content/text/` and `content/art/`) is a use and must be defined (T11), a field its schema marks `x-text` must hold one (T10), and such a line holds no `{variables}` until the engine passes some (T13). The smoke run checks that every ref a screen shows is a line.

## Real names: places and terms

A real place name or a real term isn't ours to approve (GAME_DESIGN 18.2), so it lives in `names/`, not `en/`, with the source that makes it real. Its id is `place.<id>` (the park node's id, or `places_extra.json`'s) or `term.<id>`, and its state is `place` or `term`: shippable on both channels, unless the creator cuts its words (the ledger's `cut` map, by id). A channel's `text/en.json` carries the names its data shows (S4: preview's map labels its 25 marks), and no others.

`places.json` is generated from the research's node names, cleaned: a name with a lowercase word (other than a short connective) or a `/` is a descriptive label, which is ours, so it goes in `not_places` and never names a place on a line. Fix a name at its source in `design/data/regions/`, then `npm run ingest`. A place a screen shows that isn't a park node goes in `places_extra.json`; a term in `terms.json`, when its screen first shows it.

Code that shows a place by a computed id has no literal id to give, so its call ends `// t-ids: @places`, the way content's lines end `// t-ids: @content`:

```js
tx(name, m.label); // t-ids: @places
```

Suggest's given names (S7, GAME_DESIGN Lead call 64) are terms of kind `given` (`term.given_<name>`), each sourced to the Social Security Administration's baby-name data: never the name of anyone the game knows. They are given names, and some are also surnames (B003's not-ours tail lists the nine common ones for the creator's veto, so no friend's surname reaches the field). The build ships them in `voice.json`'s `given` (with the guest book's screen), and `ui/guestbook.js` picks one by a computed id, so its call ends `// t-ids: @terms`; T16 then counts every given name as used.

A content file names a place as `"@place.lunch_lake"`. Lint T16 holds it all together: every `place.*` a build or a content file uses is a sourced place (not a `not_place`, not cut), no line's words name a descriptive label as a place, and cut words ship nowhere.

## Filed batches

A batch file is written when its lines are drafted, marked *filed, not sent*, and grows until the batch goes out (BUILD_PLAN 10.7: batches go out in the order the creator reads the game, the front door first). Once sent, it is the record and is never edited.

`review/batches.json` (S5; `schemas/batches.schema.json`) is the same record by machine: each batch's title, status (`filed`, `sent`, `answered`), the sessions that filed into it, and its lines in order, each with the FNV-1a hash of its words as filed. It was seeded from the B00n.md tables, and a test holds the two to each other, line for line. Its `held` map names the drafts kept out of every batch, each with why (S1's title page lines, retired on preview in S7; S7 filed the cover's description in B002).

```
npm run text:batch -- B004 --file [id ...] [--by S5] [--from B005]
```

files lines into a batch that hasn't gone out: the ids named, or else every draft (or changed line) on a screen the build has whose words are in no batch yet and that isn't held. Each goes into `batches.json` with its hash and as a row appended to the batch's table in B00n.md; a line already filed with the same words is left alone, so it is safe to run again. A line edited after filing is refiled in place while its batch is still unsent; once a batch has gone out, its lines come back in the next one. With `--from B00m` (S7) it moves the ids named out of another unsent batch instead: their rows leave that batch's `batches.json` list and its B00n.md table (renumbered), and join this one, so a line the cabin shows first goes out with the cabin; it refuses a sent batch, an id that batch doesn't hold, and a move with no ids. Write the B00n.md prose around the new rows by hand.

```
npm run text:batch -- B004 [--shots] [--out out/review]
```

builds the batch for review, never sending it: `out/review/B004/B004.md`, phone-readable (per screen, its numbered screenshots at the iPhone 17's size first, then a table of number, id, where, length against max and the words; a template's three sample fills from `vars.json`; a changed line's old words; a mock of the box of a line no screenshot reaches; the not-ours tail), `B004.json` (the lines, hashes, screenshot files and each badge's box, for the review page) and `shots/`. `--shots` takes the pictures with `tools/shots.mjs` (Playwright; see the main README). It warns when a batch is outside 25 to 40 lines (decision 64), and fails when a line's words changed since filing.

## Answers and `apply`

A batch goes out as `review/B00n.md`. The creator's answers become `review/B00n.answers.json`: each line's id, the FNV-1a hash of the words they saw, and the verdict (`approve`, `rewrite` with their words, `cut`, `later`, `note`, or `looks_fine` for a line with no words). Then:

```
npm run text:apply -- B00n
```

**Only `apply` writes `approved.json`,** and only for a line whose working words still hash to what the creator saw. A line edited after its batch went out stays a draft and goes in the next batch. A rewrite replaces the working words and is approved in one step. `apply` reads no clock (the dates come from the answers) and is safe to re-run. Answers files and the B00n.md records are never edited afterwards.

## The main gate

Main ships approved words only. The build fills the shell with the ledger's words, removes every `main.off` line (or its `data-t-unit`), makes the manifest from `app.name`, `app.short_name` and `app.description`, and writes `text/en.json` with the words of every id main reaches and nothing else. It fails if anything main reaches is a draft or cut, or if the built page shows any string that isn't approved words. Preview ships the working words, drafts included, and marks them in debug mode.

## The lints

- **T07:** no book words (F.3), whole words, outside `t07_allow.json`; a warning on a draft only preview shows.
- **T10:** no original English outside `content/text/`: JS sinks and English-shaped literals (developer text ends `// t-ok: <reason>`), HTML text and attributes, CSS `content:`, the manifest, SVG text.
- **T11:** every id used is defined; every line on a screen the build has is used (others wait for their screen).
- **T12:** every ledger entry matches its batch answer: same id, same hash, same words.
- **T13:** `{vars}` match the call's; `{PLACEHOLDERS}` are known and only in files allowed one.
- **T14:** the main gate, as above.
- **T15:** a line over its `max` (S5). The length is `measure()` in `web/js/text.js`: for each form (each of a plural's), the code points of the plain words, the `*` marks dropped and a line break counted as 1, with each `{var}` and `{PLACEHOLDER}` counted at its width in `vars.json`. A `{var}` with no width there fails, so a new variable comes with its width and where that comes from (`place`: the longest place name a caption can show, 21). An ours line without a whole-number `max` of 1 or more fails; a dev line is checked only when it has one.
- **T16:** the gazetteer, as above: a place missing from it, a quote that isn't its record's words exactly (from S24a's quotes), cut words anywhere.

`npm run text:check` runs them (`--main` also checks main's built words in memory); `npm run lint` runs them with everything else. `npm run text:count` prints where things stand: lines, and their words, by class and state.

## The line inspector (preview, S5)

In debug mode on preview (five taps on the build code, or `?debug=1`), a long press on any words opens a card: the line's id and the FNV-1a hash of its words, its state, its length against its max (T15's count), its batch and number there, its ctx and its words, with *Copy for chat*, which puts all of that on the clipboard to paste into a chat with your own words after it (GAME_DESIGN 18.6, 18.8). Its data is preview's `text/meta.json`, which the build writes from this folder (`tools/text.mjs metaFor`: every line's state, ctx, screen, max, length, hash and batch); main gets none, and never loads the inspector (`web/js/ui/inspect.js`). Code that sets a spoken name with `t()` (an `aria-label`) also tags the element `data-t-aria="<id>"`, so the inspector and the batch's badges find it.
